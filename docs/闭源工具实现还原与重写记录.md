# 闭源「Adobe 启动图替换器」的实现方式还原与重写记录

> 目标文件：`E:\1A-软件包\Adobe启动图替换器.exe`（5,026,304 字节，2026-08-29）
> 结论：它是开源项目 **Selorify（碎月）** 的加壳发行版，作者 DragonLingLuo；源码未公开，但实现路线可以从行为、内存与公开文档三方交叉确认。本文记录还原过程，以及我们基于同一路线、用现有技术栈重写的实现。

---

## 一、怎么查出来的（四步）

### 1. 静态分析：走不通，但拿到了关键指纹

PE 头解析结果：

| 项 | 值 | 含义 |
|---|---|---|
| Machine | `0x014C` | 32 位 |
| OptionalMagic | `0x010B` | PE32 |
| CLR 目录 | RVA 0 / Size 0 | **没有** .NET 头 |
| 节数 | 6 | 节名除 `.rsrc`、`.data` 外全为 `\0` |
| 各节熵 | **8.00 / 8.00 / 7.94 / 8.00** | 完全加密 |
| 可打印字符串 | 全文仅 **1429** 条 | 5MB 文件只剩这么点明文 |

结论：被商业壳加密，`反编译` 这条路成本极高。字符串里命中 **`Enigma` ×7**，节名清空 + 全节高熵是 Enigma Protector 的典型特征。

### 2. 行为分析：窗口类名暴露了真实技术栈

以独立进程启动后枚举窗口，得到：

```
HwndWrapper[Adobe启动图替换器.exe;;107ddef5-…]  title='Selorify-免责声明'
HwndWrapper[Adobe启动图替换器.exe;;2d8f8d10-…]  title='Selorify'
MediaContextNotificationWindow
SystemResourceNotifyWindow
```

`HwndWrapper[...]`、`MediaContextNotificationWindow`、`SystemResourceNotifyWindow` 都是 **WPF（PresentationCore）** 的内部窗口。也就是说：**它原本是个 .NET WPF 程序，被 Enigma 套壳后 CLR 头被抹掉了**。真实产品名是 `Selorify`。

### 3. 内存取证：把壳解出来的东西捞回来

Enigma 在运行时必须把原始程序集解密到内存。直接 `ReadProcessMemory` 遍历已提交可读区域，提取字符串，得到决定性证据：

```
!github.com/DragonLingLuo/Selorify
SelorifyViewModel
\Selorify\ExEffect\ExEffect\obj\Debug\net45\ExEffect.pdb
&dlllibrary/icsharpcode.sharpziplib.dll
请选择你要修改的软件或你要修改的软件的快捷方式
拖入快捷方式或选择路径以开始
请选择你要用来替换的图片
备份创建成功 / 备份失败 / 备份位于:
当要恢复备份时直接右键"解压到当前文件夹"-"替换"-"全部选是"即可。
【目标(未修改)】

```

信息量很大：
- 主程序 `Selorify`（WPF + MVVM，`SelorifyViewModel`），子项目 `ExEffect`，目标框架 **.NET Framework 4.5**；
- 引用 **SharpZipLib** → 备份是 **ZIP 压缩包**，还原靠解压覆盖；
- 输入方式是 **快捷方式 / 路径**，不是选安装目录；
- 有 `【目标(未修改)】` 这种「改前/改后」对照展示。

反证同样重要：**`pr_splash`、`idrc`、`PSIcons`、`LRC_SPLASH`、`ai_cc_splash`、`AuUI`、`LAUNCHAME`、`AfterFXLib` 这些教程里的文件名，一个都没有出现在内存里**。说明它不靠「文件路径表」定位，而是靠 **PE 资源名表**。

### 4. 公开文档：README 把方法说全了

`https://github.com/DragonLingLuo/Selorify` 的 README 明确写了：

- 定位：「一个对于 Adobe 个人觉得常用的设计类软件（Ps、Ai、Id、Lr、Fl(An)、Pr、Ae、Au、Me）的启动界面修改工具。只需要将目标程序的快捷方式或者可执行文件拖入窗口或者用按钮选择或者直接输入路径，程序可自动识别、另存启动图片、生成预览，修改时自动备份等」
- 支持范围：PS 3.0–2026、AE 3.1/CS3–2026、PR CS6–2026、AU CS6–2026、An CC 2015–2024、CH 2020–2026、Lr 4–Classic 2026、AI CS6–2026、ID CS6–2026、IC 2020–2026、ME CC 2014–2026、Premiere Rush 1.x–2.x
- 已知限制（原文）：
  1. 「如果修改后的图像和修改之前的**尺寸**差别非常大……可能会导致目标崩溃」→ **它不缩放图片**，直接按用户图原样写入；
  2. 「如果目标位于需要管理员权限才能修改的目录，而未以管理员权限运行本程序，那么可能导致即便提示修改成功……但是实际上没有成功」；
  3. 「由于 Windows 的 UIPI 限制，以管理员身份运行时，向程序中拖拽文件识别可能会失效」；
  4. 远古版本「某些版本的资源有加密（比如 Ae 6.0-7.0），得想办法先破解」。
- 源码：「等再过几个版本我改好一点再把源码放上来」→ **至今未公开**。

## 二、它的核心方法（还原结论）

```
用户拖入 exe / .lnk / 输入路径
        ↓
解析快捷方式 → 真实 exe → 识别「哪个软件 + 哪个版本」
        ↓
查内置的「软件 × 版本 → 资源名」表，定位承载启动图的文件与资源名
        ↓
枚举 PE 资源 → 取出原启动图 → 另存 / 预览
        ↓
用户选图 → 按原资源名把新图写回（不缩放，长度可变）
        ↓
写之前把原文件打进 ZIP 备份；失败/无权限时提示以管理员运行
```

**关键判断：它走的是 PE 命名资源（`UpdateResource` 这一类 API），不是「改磁盘上的 png 文件」。**
依据有两条，互相独立：
1. 内存里没有任何 `pr_splash` / `ai_cc_splash` 之类的文件路径串，却有完整的 WPF 资源枚举/预览功能；
2. 对 AE 这种把启动图放在 `AfterFXLib.dll` 里的程序，除资源重写外没有第二条路（见第三节实测）。

## 三、我们重写时做了什么不同

| 维度 | Selorify | 本次实现 | 为什么改 |
|---|---|---|---|
| 定位方式 | 内置「软件 × 版本 → 资源名」表 | **扫描目标目录下所有 PE 文件的 PNG 资源**，按名称/尺寸打分排序 | 那张表要覆盖 13 个软件 × 30 年版本，是巨大的维护负担，且新版本一发布就失效。扫描法对「表里没有的版本」同样有效 |
| 尺寸处理 | 不缩放，尺寸差太多会崩溃（作者自述） | 写入前按原资源尺寸渲染：**等比裁切**（默认，不变形）或拉伸 | 直接消灭它最大的已知坑 |
| DPI 变体 | 未见说明 | 识别 `_AT_2X` / `_AT_3TO2X` 等后缀，**同组自动一起替换** | AE 有 1x/1.5x/2x 三份，只改 1x 在高分屏上看不到变化 |
| 备份 | ZIP 包，解压覆盖还原 | 每个目标文件独立 `.bak` + 清单，UI 一键还原 | 更细粒度，能只还原某个文件；也不要求用户会解压 |
| 提权 | 提示「请以管理员运行」 | 写入失败自动走 `--elevated` 通道重试 | 省掉「提示成功其实没成功」这类静默失败 |
| 输入 | exe / lnk / 手输路径 | 同上，另加**拖放**（UIPI 下会提示改用按钮） | 保持习惯一致 |

**没有照搬的部分**：内置资源名表、不缩放、ZIP 备份。这三处都是有意的取舍，不是遗漏。

## 四、实测数据（AE 2026，全部在副本上进行）

沙箱：把 `AfterFXLib.dll`（49,345,032 字节）与 `AfterFX.exe` 复制到临时目录后操作。

### 4.1 扫描

```
候选启动图 26 项（含 MLFoundation.dll 里 3840×2160 的大图）
首选：AE_SPLASH  766×516  378,645 字节
排序：AE_SPLASH → AE_SPLASH_AT_2X → AE_SPLASH_AT_3TO2X → AE_BETA_SPLASH …
```

同组识别正确：`AE_SPLASH` 组 3 项、`AE_BETA_SPLASH` 组 3 项，互不串组。

### 4.2 写入

```
替换项    : AE_SPLASH, AE_SPLASH_AT_2X, AE_SPLASH_AT_3TO2X
原始大小  : 49,345,032
写入后    : 47,092,224      ← 变小，因为替换图是纯色、压缩后更小
自检      : 资源 3 项写回成功，PE 结构自检通过
兄弟资源  : AE_BETA_SPLASH 三张原封不动
```

**长度可以自由变化**（3 项从 378,645/1,195,050/723,176 字节分别变成 8,595/32,784/18,770），这正是 `UpdateResource` 与达芬奇那套「等长原地覆盖」的本质区别。

### 4.3 还原

```
还原后 sha256 = e0b699f4d85df5e7  与原件一致 = True
还原后大小    = 49,345,032
```

逐字节一致，闭环成立。

## 五、边界情况（重写时必须处理的）

| 边界 | 现象 | 处理 |
|---|---|---|
| 目标程序正在运行 | 文件被占用，写入失败 | 写入前检查 AfterFX / Premiere Pro / Media Encoder / Audition / Animate / Character Animator / Lightroom 等进程 |
| 目标在 `Program Files` | 非管理员写不进去 | 生成补丁副本 → 部署失败 → 自动提权重试 |
| 管理员模式下拖放 | UIPI 拦截，拖进来没反应 | 保持「浏览…」按钮可用，日志提示 |
| 高分屏 DPI 变体 | 只改 1x 时 150%/200% 屏看不到变化 | 同组自动替换，UI 明示「将写入 N 个资源」 |
| 宽高比不符 | 拉伸变形 / 裁切掉内容 | 默认等比裁切，可切到拉伸 |
| 资源名不带 splash | 例如只叫 `LAUNCHAMEBACKGROUND` | 兜底规则：横向且 ≥500×400 也算候选；再加「显示全部 PNG」开关 |
| 非 PNG 容器的程序 | PS 的 `.idx + .dat`、ID 的 `.idrc` | 扫不到就明确告知「该程序可能不使用 PNG 资源」，不假装成功 |
| 签名 | 改完全家桶签名失效 | 确认框里写明；AE 的 `AfterFXLib.dll` 本来就是 `HashMismatch` |
| 反复修改 | 备份被后来的「已改文件」覆盖 | 备份只写一次，已存在就复用最早那份 |

## 六、验证方式

1. **不碰真机**：所有写入先在 `%TEMP%` 的副本上跑，验证通过才部署。
2. **写后自检**：重新枚举资源比对字节数 + `LoadLibraryExW(LOAD_LIBRARY_AS_DATAFILE)` 确认 PE 结构没坏。
3. **还原校验**：还原后比 sha256，必须与原始副本完全一致（实测通过）。
4. **界面回归**：直接启动看列表排序、预览、按钮可用性。

> 说明：`AE 启动时真的显示新图` 这一条无法静态验证，需要实际启动一次 AE 肉眼确认——这是唯一未闭环项。

## 七、附带发现（与本工具无关，但值得知道）

`C:\Program Files\Adobe\Adobe After Effects 2026\Support Files` 下有 7 个 `.bak`，时间戳全部是 **2026-10-17 17:14**，其中：

- `AdobeCrashReport.exe`、`CRLogTransport.exe`、`crashpad_handler.exe` 三个崩溃上报程序**原文件已被删除**，只剩 `.bak`；
- `AfterFXLib.dll` 与它的 `.bak` 相比，在偏移 `0xEF9E6C` 处有 3 字节差异：
  ```
  原: c3 32 c0 c3   (ret; xor al,al; ret)
  现: 90 b0 01 c3   (nop; mov al,1; ret)
  ```

这是一个把布尔函数强制返回 `true` 的字节补丁，配合删除崩溃上报程序，属于典型的**授权/防崩溃补丁**特征，不是 Adobe 安装器也不是本工具做的。

两点影响：
1. 我此前把 `AfterFXLib.dll` 的 `HashMismatch` 归因于「Adobe 自己改过」是错的，实际来自这次第三方修改——**结论不变**：这个文件本来签名就无效，改不改都一样。
2. 我们的写入走 `UpdateResource`，会保留 `.text` 段里已有的补丁字节（实测还原后 sha256 与修改前一致），不会破坏已有补丁。
